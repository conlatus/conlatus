# Devlog: Dynamic Interview Links & Candidate UI 🚀

**Date:** 2026-08-17
**Feature:** Dynamic Interview Configurations & Candidate Experience

Grab your coffee ☕, because we just shipped a massive quality-of-life update to Conlatus! 

## What just happened?
Previously, the backend was entirely hardcoded with a single AI persona, standard questions, and a monolithic rubric tucked away in `rubric_config.py`. While great for an initial proof of concept, this meant every single candidate got the exact same interview. Boring! 

Today, we tore that limitation down. We completely refactored the backend architecture to support **Dynamic, Per-Session Configurations**. 

### The Under-the-Hood Magic 🪄
1. **In-Memory Config Store**: We built `InterviewConfigStore` in the FastAPI backend to securely cache custom interview setups generated by the admins.
2. **Frontend Wiring**: The `/admin/setup` page now actually talks to our new `POST /admin/interviews` API endpoint. Instead of just logging an object to the console (classic developer move 😂), it now returns a proper `interview_id`.
3. **Slick UI Updates**: We've updated the setup page to show a very satisfying success state where the admin can one-click copy the newly minted, shareable interview link.
4. **The Candidate Journey**: We built a sleek, dark-themed UI at `/interview/[id]` for the candidate. This page mounts up, parses the `interview_id` from the URL, pings the backend to establish a session, and loads the specific `InterviewConfig` assigned to that ID. 

### The "Oops" Moment
The tricky part? Refactoring `llm.py` so that it uses the dynamically passed `rubric_criteria` from the active session instead of defaulting to the global `rubric_config.py`. It required a bit of parameter-passing gymnastics through `start_interview` and `_process_candidate_turn`, but we handled it with optional fallback logic to keep tests from breaking. 

Overall, a solid ship. The platform now actually supports custom interviews on the fly!

Until next time, keep coding! ✌️
